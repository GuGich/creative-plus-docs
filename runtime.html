Как работает код

Выбор целей, условия, ожидания, функции, циклы, ошибки и ограничения выполнения.

5. How code runs

5.1 Targets of a line ("selection")

Every node works on a list of targets called the selection.

  • Event line: the selection starts as the default target of the event.
  • PLAYER_* events: the player of the event. Example: in PLAYER_KILL_PLAYER it is the killer; the killed player is VICTIM.
  • ENTITY_* events: usually the entity of the event. Some entity events use a player instead (for example ENTITY_KILL_PLAYER: default = the killed player, the mob is %entity% / DEFAULT_ENTITY).
  • PLOT_* events: usually the world default: the first player in the world, or the last spawned entity when no player is there. The exact starting target of every event is in its default target line in the event catalog. If that player is in coding mode, the selection is empty.
  • Loop: on each run the selection is every player in play mode who stands inside the plot. With no such players the selection is empty.
  • Function: the selection of the caller at the moment of the call.
  • An action runs once for EACH target in its selection. This is true also for world and variable actions. In a loop with 5 players, VARIABLE_INCREMENT adds 5 times. Use SELECT_RANDOM_PLAYER (or another select) first if you need one run.
  • Players who are not in play mode (for example coding) or not in the plot world are removed from the selection before an action runs.

5.2 Selection actions

  • SELECT_* (category CREATE_SELECTION) replace the selection, SELECT_ADD_* add to it, SELECT_FILTER_* remove from it.
  • The exact rule (one line run):
  • A SELECT_* changes the selection for all following nodes of the same node list.
  • The children of a bracket start with the selection made by the LAST SELECT_* that ran in this line run, even if that select was inside an earlier bracket. If no select ran yet, they start with the line's starting selection.
  • When a bracket ends, the nodes after it continue with the selection they had before the bracket. A select inside the bracket does not change them.
  • GAME_WAIT saves the same selection as rule 2 (see 5.5).
  • A function gets a copy of the caller's current selection. A SELECT_* inside the function never changes the caller's selection.
  • Safe habit: when a bracket or a GAME_WAIT must work on a certain group, put the SELECT_* right before it in the same list, or as the first child of the bracket. Never rely on rule 2 picking up a select from an earlier bracket.
  • SELECT_PLAYERS_BY_CONDITION, SELECT_MOBS_BY_CONDITION, SELECT_ENTITIES_BY_CONDITION, SELECT_ADD_*_BY_CONDITION and SELECT_FILTER_SELECTION_BY_CONDITION need a condition key with ONE condition node. The condition is tested for each candidate alone. "not": true on that condition works. Do not give it children. Put the condition's args and switches INSIDE the condition node (the server copies them to the selection block).
{"action": "SELECT_PLAYERS_BY_CONDITION", "condition": {"action": "IF_PLAYER_SNEAKING"}}

5.3 target on one node

target changes the targets of ONE node only. The selection of the line does not change. The node then runs once for EACH target of the new list, exactly like with a normal selection.

Example: in PLAYER_JOIN, {"action":"PLAYER_MESSAGE","target":"ALL","args":{"texts":"§e%player% joined"}} sends the message once to every player in play mode. %player% stays the player who joined; %selected% is the receiver. With "target":"ALL" a VARIABLE_INCREMENT adds once per player.

On a condition, target only changes WHO is tested. The children still run for the line's selection (section 5.4).

Player target list (all nodes except IF_ENTITY conditions):

| target | who |
|---|---|
| `SELECTION` | current selection (default) |
| `DEFAULT` | default target of the event |
| `RANDOM` | one random player of the world. It is picked from ALL players there, coders too; if a coder is picked, the node does nothing this time |
| `ALL` | every player of the world who is in play mode. Players who are coding are not included |
| `KILLER` | the killer from the event |
| `DAMAGER` | the attacker from the event |
| `SHOOTER` | the shooter from the event |
| `VICTIM` | the victim of a damage or kill event |

Entity target list (only for IF_ENTITY conditions):

| target | who |
|---|---|
| `CURRENT` | current selection (default) |
| `DEFAULT` | default target of the event |
| `DEFAULT_ENTITY` | the entity of the event |
| `KILLER`, `DAMAGER`, `SHOOTER`, `PROJECTILE`, `VICTIM` | from the event |
| `RANDOM_ENTITY` | one random non-player entity in the world |
| `ALL_MOBS` | all living non-player entities |
| `ALL_ENTITIES` | all non-player entities |
| `LAST_LIVING_ENTITY` | the last living entity spawned by code |
  • Write targets in UPPER CASE. An unknown target is a warning (UNKNOWN_TARGET) and works as the default.
  • If the event has no killer/damager/etc., that target is empty and the node does nothing.
  • target is ignored on selection nodes, GAME_WAIT and function calls.
  • In PLAYER_* events, IF_ENTITY conditions without a target test the event entity (if there is one).

5.4 Conditions, ELSE, else-if

  • A condition node has children. If the condition is true, the children run. Then the line continues after the condition.
  • A condition gives ONE true/false for the whole selection. It does not filter: the children run for the whole selection (rule 2 in 5.2), not only for the targets that passed. To keep only the players that pass, use SELECT_FILTER_SELECTION_BY_CONDITION (or SELECT_PLAYERS_BY_CONDITION) instead of a bracket.
  • "not": true inverts the result.
  • How several targets combine depends on the condition (see the catalog). Many player conditions need all targets to pass; many variable conditions only look at the first target. With an empty selection the result may be true or false depending on the condition. Avoid conditions on an empty selection: to count players by a condition and then decide, set the counter, select by condition, VARIABLE_INCREMENT, then SELECT_ALL_PLAYERS (or SELECT_RANDOM_PLAYER) BEFORE the condition that reads the counter.
  • ELSE: put {"action":"ELSE","children":[...]} DIRECTLY after the condition. It runs when the condition was false.
  • Else-if: put another condition with "elseIf": true directly after the first condition (or after another else-if). It is tested only when all conditions before it in the chain were false. Then an ELSE may follow.
  • The chain is: one normal condition, then any number of elseIf conditions, then optionally one ELSE. Any other node between them ends the chain.
  • An ELSE or elseIf condition that does not directly follow a chain never runs.
  • Do not use the ELSE_IF action. It is an empty editor block. Use "elseIf": true on a condition.
{"action":"IF_VARIABLE_EASY_COMPARE_NUMBER","args":{"num1":{"var":"x"},"num2":10},"switches":{"state":0},"children":[ ... ]},
{"action":"IF_VARIABLE_EASY_COMPARE_NUMBER","elseIf":true,"args":{"num1":{"var":"x"},"num2":5},"switches":{"state":0},"children":[ ... ]},
{"action":"ELSE","children":[ ... ]}

5.5 Waiting: GAME_WAIT

{"action":"GAME_WAIT","args":{"duration":3},"switches":{"state":1}}

  • duration: a whole number. state: 0 = ticks (default), 1 = seconds, 2 = minutes.
  • The rest of the CURRENT node list runs later. The selection is saved at the moment of the wait: it is the selection of the last SELECT_* that ran in this line run (rule 2 in 5.2). Without brackets this is simply the current selection.
  • Inside a bracket or a function, only the rest of that bracket or function waits. The nodes after the bracket (or after the function call) run at once, without waiting.
  • If the selection is empty when GAME_WAIT is reached, the rest of the list is dropped.
  • Longest wait: 30 minutes. Longer waits stop the code run.
  • Waits are cancelled when the world leaves play mode or the code restarts.

5.6 Functions

  • Define: {"kind":"function","name":"reward","nodes":[...]}.
  • Call: {"action":"CALL_FUNCTION","args":{"name":"reward"},"switches":{"async":0}}.
  • args.name must be a TEXT value and not blank (EMPTY_NAME).
  • async: 0 = run now and continue after it finishes (default); 1 = run on the next tick, the caller does not wait.
  • GAME_CALL_FUNCTION_WITH_VARIABLE does the same, but the name is read for every target, so the name can contain placeholders or a variable.
  • The function gets the caller's current selection and the same event (event values and %player% are those of the caller's event). Selects inside the function do not change the caller's selection: after the call the caller goes on with its own selection.
  • Unknown function name: nothing happens, no error.
  • Color codes are ignored when a function or loop is looked up by name (§aReward = Reward).
  • If the selection is empty, the call does nothing.

5.7 Loops

  • Define: {"kind":"loop","name":"timer","ticks":20,"nodes":[...]}.
  • A loop does NOT start by itself. Start it with {"action":"GAME_START_LOOP","args":{"names":"timer"}} and stop it with GAME_STOP_LOOP.
  • GAME_START_LOOP needs a non-empty selection (it runs once per target; starting a running loop does nothing).
  • Starting a loop that already runs does NOT restart its countdown. A new loop runs for the first time ticks ticks after the start, not at once.
  • GAME_STOP_LOOP only stops future runs. A run that is going on right now (also the loop stopping itself) finishes its nodes, and nodes waiting after a GAME_WAIT in that run still run later. The remaining countdown is remembered: a later GAME_START_LOOP continues it, it does not start from 0.
  • A loop starts a new run every ticks ticks even if the last run is still waiting in GAME_WAIT.
  • Every run of a loop uses the event and target of the GAME_START_LOOP call that started it: %player% and event values inside the loop are those of that start.
  • Good place to start loops: PLAYER_JOIN (it runs for every player when the world starts and when someone enters).
  • Loops stop when the code restarts. The code restarts when the world switches to play mode, after an import, and when the first player enters an empty world. So also create bossbars and scoreboards and start loops in PLAYER_JOIN; creating an existing bossbar or scoreboard does nothing.

5.8 Errors and limits while running

  • If an action fails, all players in the world get a chat message "error executing ..." (click teleports coders to the block). The line continues with the next node.
  • Every world has limits for actions, messages, variable writes, waiting timers, teleports, entities, particles, memory and CPU time. They grow with the number of players. Normal games do not reach them.
  • If a limit is exceeded, the current run of the line stops and the owner gets a message. If it happens too often, the world is switched to build mode (all code stops). Fix the code as in section 14.9.
  • Avoid heavy work in fast events (PLAYER_MOVE, PLAYER_TURNS_AROUND) and in loops with small ticks.

5.9 What happens when (the life of a world)

| moment | what the server does | events, in this order |
|---|---|---|
| The owner switches the world to play mode (`/play` in build mode), or code is imported while the world plays | The code restarts. Every player who is not coding is prepared and moved to the spawn. | `PLAYER_JOIN` for each player, then `PLOT_WORLD_STARTS` once |
| A player enters a world that is in play mode | If nobody was in the world, the code restarts first. The player is prepared and moved to the spawn. | `PLAYER_JOIN` only. `PLOT_WORLD_STARTS` does NOT run |
| A player who is playing types `/play` | The code does NOT restart: variables, loops, waits and entities stay. The player is prepared again and moved to the spawn. | `PLAYER_REJOIN`, `PLAYER_QUIT`, `PLAYER_JOIN` |
| A coder types `/play` | The code restarts for the whole world. Only this player is prepared and moved. | `PLAYER_JOIN` |
| The owner switches the world to build mode (`/build`) | All code stops. | `PLOT_WORLD_STOPS` |
| A player dies | 5 ticks in spectator mode, then the old game mode back and a move to the spawn (a game mode that `PLAYER_DEATH` sets stays: it runs after this). The items drop at the death place, unless `PLAYER_SET_DEATH_DROPS` keeps them (items with Curse of Vanishing are lost). | `PLAYER_DEATH`, then `PLAYER_KILL_PLAYER` or `ENTITY_KILL_PLAYER` |
| A player leaves the world | | `PLAYER_QUIT` |
  • "The code restarts" means: variables without save are deleted, loops stop, waiting GAME_WAITs are dropped. Saved variables stay, also when NEW code is imported: a new version of a game sees the saved data and scoreboards of the old one. If the new version must start clean, give its saved variables and scoreboards new names (or remove old scoreboards with GAME_REMOVE_SCOREBOARD).
  • Scoreboards, bossbars and holograms made by code survive a restart with their old lines and titles. Creating them again does nothing, so set their lines again when a round starts.
  • Entities spawned by code (mobs, visualizers, dropped items) are never removed by the server: they stay through restarts, build mode and server restarts, because they are saved with the world. Remove them yourself (section 14.1).
  • "Prepared" means: inventory, armor and off hand cleared, effects removed, full health and food, adventure mode, no flying. The last hotbar slot (slot 8) may then get the world compass (the owner always gets one, right after PLAYER_JOIN), so do not put game items into slot 8.
  • The spawn is where players appear. In PLAYER_JOIN the player already stands there, so CURRENT_LOCATION is the spawn.

6. Variables

{"var":"coins_%player_uuid%","save":true}

  • All variables are global for the whole world (plot). There is no per-player scope. For per-player data put %player_uuid% or %player% into the name. The name is read with placeholders when the node runs.
  • %player_uuid% is ALWAYS the player of the event, also when the node runs for other selected players. In a node that runs for several selected players (after SELECT_ALL_PLAYERS, in a loop, with "target":"ALL"), write %selected_uuid% (or %uuid%): it is the target the node runs for right now. Example: reset a flag of every player with SELECT_ALL_PLAYERS, then VARIABLE_SET on {"var":"dead_%selected_uuid%"}.
  • save:true: the variable is stored with the world and survives restarts.
  • save:false: the variable lives in memory only. It is cleared when the code restarts (see 5.7).
  • The save flag of the node that WRITES decides. Writing the same name with save:false makes a saved variable unsaved. Use the same save value for one name everywhere.
  • Reading a variable that does not exist gives nothing: numbers read as the default (often 0), texts as empty.
  • Names: up to 1024 chars. Color codes are removed from names.
  • A list variable and a normal variable may have the same name. They do not mix. Use "collection":"LIST" on a variable that holds a list, "collection":"DICT" for a dictionary and "collection":"SET" for a set. It is optional for reading but helps the editor show the right item.
  • Actions write results into the argument of type VARIABLE (often called variable, output or similar; see the catalog).
  • Numbers are stored as decimals. A number variable or number value printed in text (%var(x)%, a variable or a JSON number in a TEXT argument, %math(...)%) has no trailing zeros: 5.0 is shown as 5, 2.50 as 2.5. Other digits are NOT cut: 10 / 3 is shown as 3.3333333333333335, 0.1 + 0.2 as 0.30000000000000004.
  • To show fewer digits, round first with VARIABLE_ROUND (scale = digits after the dot; marker state: 0 = normal, 1 = down, 2 = up), then print the variable:

{"action":"VARIABLE_ROUND","args":{"variable":{"var":"avg"},"number":{"var":"avg"},"scale":2}} turns 3.3333… into 3.33.

Inside text you can also write %math(round(%var(avg)% * 100) / 100)%. Note: round in %math% rounds a half to the even number (round(2.5) = 2).

  • A game value put straight into a TEXT argument, or read with %value(...)%, may be printed in raw form: 20.0 instead of 20, or many digits (health 17.833333492279053). To print it cleanly, first copy it into a variable (VARIABLE_SET, or VARIABLE_ROUND with the game value as number) and print %var(...)%.
  • Numbers INSIDE a list, set or dict are printed with .0: a list of 1, 2 is shown as [1.0, 2.0].
  • Readable list text: put the list variable into a TEXT value or write %var(name)%. A list prints as [a, b, c] (values joined with , , in square brackets), a set as (a, b), a dict as {key=value, key2=value2}. To drop the brackets, use VARIABLE_REPLACE_TEXT on that text. LIST_TO_STRING is NOT a join: it writes a multi-line debug text (`<Array name (3) >, then #0 = a per element counting from 0, then </Array name>`). Do not show it to players.

7. Text, placeholders, colors

7.1 Placeholders

They work in TEXT values, in variable names and in texts read as numbers.

Where placeholders are replaced:

  • Almost every argument: TEXT arguments (also single keys such as DICT_GET_BY_KEY key, scoreboard and bossbar names, function names), texts given to NUMBER arguments, variable names, COMPONENT values, list/dict/set variable names, and text values in ANY arguments (VARIABLE_SET values, LIST_APPEND values, LIST_CREATE_OR_CLEAR values and similar).
  • NOT replaced (text is used as written), each one is noted in its catalog entry: obj of IF_VARIABLE_EQUALS / IF_VARIABLE_NOT_EQUALS (put the text into objects instead), value of LIST_INSERT and LIST_REPLACE_BY_INDEX, channel_name of the data transfer actions, and a few others. When a catalog note says "NOT replaced" or "read as written", believe it.
  • Texts INSIDE a literal list, dict or set value ({"list":["%player%"]}) are stored as written. Use LIST_APPEND with text values if you need the replaced text in a list.
| placeholder | value |
|---|---|
| `%player%`, `%player_uuid%` | name / UUID of the event player (the default target if it is a player) |
| `%default%`, `%default_uuid%` | default target of the event (player or entity) |
| `%selected%`, `%selected_uuid%`, `%uuid%` | the target the node is running for right now |
| `%selection%`, `%selection_uuid%` | all targets of the node, joined with `,` (cut at 1024 chars) |
| `%damager%`, `%shooter%`, `%projectile%`, `%killer%`, `%victim%` (+ `_uuid`) | from the event |
| `%entity%`, `%entity_uuid%` | the entity of the event |
| `%random%`, `%random_uuid%` | a random online player of the world |
| `%var(name)%` | value of variable `name` (empty if missing). The name may contain placeholders: `%var(coins_%player_uuid%)%` |
| `%value(ID)%`, `%value(ID, SEL)%` | a game value by id. Without SEL it is read for the event's default target. SEL is the same list as in section 8. |
| `%math(expression)%` | calculation result |
  • The short placeholders are lower case and exact. %var(, %value( and %math( ignore case.
  • A placeholder with no entity (%killer% in a join event) or an unknown %value(ID)% becomes empty text. A misspelled placeholder or a bad %math(...)% stays as written.
  • Math: + - * / % ^, brackets, constants pi, e, functions sin cos tan ctg asin acos atan atan2 sinh cosh tanh rad deg sqrt cbrt abs log log2 log10 exp ceil floor sign round pow(a,b) min(a,b) max(a,b) mod(a,b) fact(n) clamp(x,min,max) lerp(a,b,t) dist(a,b) randint(a,b) random(a,b) randfloat(a,b). randint(a,b) and random(a,b) both give a whole number from a to b-1 (if a >= b the placeholder stays unchanged); use randfloat(a,b) for a decimal. Trig functions use radians. Division by zero or a bad expression leaves the placeholder unchanged. Example: %math(%var(score)% * 2 + 1)%.

7.2 Colors

  • Use § color codes in TEXT: §a green, §c red, §e yellow, §6 gold, §7 gray, §f white, §l bold, §r reset.
  • & is NOT converted in JSON. Write §.
  • Hex: §#RRGGBB (this is what the in-game input &#RRGGBB becomes). Plain § codes are the safest.

8. Game values

{"val":"CURRENT_HEALTH","sel":"KILLER"}

  • A game value is read at the moment the node runs, for the target being processed.
  • sel matters only for values that depend on an entity (hasSelection in the value catalog). Options: CURRENT (the target being processed; same as no sel), DEFAULT, DEFAULT_ENTITY, KILLER, DAMAGER, SHOOTER, PROJECTILE, VICTIM, LAST_LIVING_ENTITY. Unknown text = default target.
  • Categories (full list in the value catalog):
  • ENTITY_STATISTIC: CURRENT_* values of the target, such as health, food, name, UUID, ping, game mode.
  • LOCATION_VALUE: positions of the target (CURRENT_LOCATION, CURRENT_EYE_LOCATION, block under it, and so on).
  • ITEM_VALUE: items of the target (MAIN_HAND_ITEM, armor, and so on).
  • WORLD: world values such as PLOT_ONLINE, PLOT_ID, CURRENT_UNIX_TIME (milliseconds), CURRENT_TIMESTAMP.
  • PLOT_ONLINE counts EVERY player in the world, also players who are coding. There is no game value for "players in play mode" or for the number of mobs. Count them with a selection: set the counter to 0, select, then VARIABLE_INCREMENT (it runs once per selected target). Put the VARIABLE_SET BEFORE the select, and select again afterwards if the following nodes need another selection:

{"action":"VARIABLE_SET","args":{"variable":{"var":"playing"},"values":0}},

{"action":"SELECT_ALL_PLAYERS"},

{"action":"VARIABLE_INCREMENT","args":{"variable":{"var":"playing"}}}

For mobs use {"action":"SELECT_MOBS_BY_CONDITION","condition":{"action":"IF_ENTITY_IS_MOB"}} instead of SELECT_ALL_PLAYERS (living non-player entities; armor stands count too). With nothing selected the counter stays 0. The first node needs a non-empty selection to run, so in a loop with no players nothing is counted.

  • EVENT_VALUE: data of the current event (EVENT_*).
  • Event values are game values too. In an event that does not give that data they return 0, empty text or nothing. Common pairs (event data key → value id): message → EVENT_CHAT_MESSAGE, damage → EVENT_DAMAGE, final_damage → EVENT_FINAL_DAMAGE, damage_cause → EVENT_DAMAGE_REASON, block → EVENT_BLOCK (as item) and EVENT_BLOCK_LOCATION, item → EVENT_ITEM, from/to → EVENT_OLD_LOCATION/EVENT_NEW_LOCATION, clicked_slot → EVENT_CLICKED_SLOT, exp_amount → EVENT_EXP_AMOUNT.
  • Cancellable events (marked * below) can be cancelled with GAME_CANCEL_EVENT. Do it before any GAME_WAIT.

PLAYER_CHAT does NOT fire for: messages that start with ! (the server cancels them and tells the player that global chat is off), commands (/...), players who are coding, worlds that are not in play mode, and messages that were already cancelled. So never design a chat command that starts with !; use another prefix, for example # or .. Put GAME_CANCEL_EVENT first, before other work and before any GAME_WAIT.

PLOT_DATA_TRANSFER receives data sent by PLOT_DATA_TRANSFER_WRITE or PLOT_DATA_TRANSFER_WRITE_LIST from another world of the SAME owner. The line runs only when its channel equals the channel of the message.

10. Size limits

  • Lines: at most 23 per code floor. A plot with N floors accepts at most 23 × N lines (TOO_MANY_HANDLERS). A new plot may have only 1 floor, so keep to 23 lines unless the player says they have more floors.
  • Line width: at most 92 blocks (LINE_TOO_WIDE). Count it like this:
  • starter block: 2;
  • each normal node (action, selection, GAME_WAIT, call, GAP): 2;
  • each bracket (condition or ELSE): 4 + the width of its children.
  • Example: starter + 10 actions + one condition with 5 actions = 2 + 20 + (4 + 10) = 36.
  • If a line gets too wide, move part of it into a function.
  • The number of nodes, brackets inside brackets and the size of one value are limited too (TOO_MANY_NODES, CONDITION_TOO_DEEP, VALUE_TOO_LARGE). Normal games do not reach these limits.

11. Problems the server reports

Blocking problems reject the import. Warnings let the import continue (after confirmation), but the broken part will not work. Fix warnings too.

| code | blocking | cause | fix |
|---|---|---|---|
| EMPTY_PROGRAM | yes | no valid handlers | add at least one handler |
| BROKEN_HANDLER | yes | a handler could not be read: bad `kind`, missing `event`/`name`, a node without `action`, a non-object in `nodes`, or any malformed value inside it (`loc` with fewer than 3 numbers, a non-integer switch; `kind` is case-sensitive) | follow section 3.2 and 3.3 |
| EMPTY_NAME | no | function/loop with blank `name`, or `CALL_FUNCTION` without a text `args.name` | give a name |
| LINE_TOO_WIDE | yes | line wider than 92 | split into functions |
| BAD_NAME | yes | a function/loop name, a `CALL_FUNCTION` name or a `channel` is longer than 256 chars or is not plain text; or an action, event or `target` id is longer than 64 chars | plain short name, real id |
| VALUE_TOO_LARGE | yes | one value (one slot) is too large (a huge text, list, map, component or item) | smaller value |
| CHILDREN_REQUIRED | yes | a condition or `ELSE` without `children` | add `children` (may be `[]`) |
| CHILDREN_NOT_ALLOWED | yes | `children` on an action, selection or other control | remove `children` |
| NOT_CONDITION | yes | `not`/`elseIf` on a non-condition, or `condition` holds a non-condition | use them only with conditions |
| CONDITION_NOT_ALLOWED | yes | `condition` on a node that is not a selection | remove it, or use a `SELECT_*_BY_CONDITION` action |
| TOO_MANY_HANDLERS | yes | more lines than 23 × floors | fewer lines |
| TOO_MANY_NODES | yes | too many nodes | smaller program |
| CONDITION_TOO_DEEP | yes | too many nested brackets | flatten, use functions |
| BAD_ITEM | yes | the item cannot be read or is too heavy | use a simple normal item |
| JSON_TOO_LARGE | yes | the program is too large | smaller program |
| MARKER_OUT_OF_RANGE | yes | switch value not in 0..options-1 | use a listed option index |
| TOO_MANY_VALUES | yes | more values than the argument's `max` | fewer values |
| UNKNOWN_ACTION | no | action id does not exist | use an id from the catalog |
| UNKNOWN_EVENT | no | event id does not exist (the line never runs) | use an id from section 9 |
| UNKNOWN_GAME_VALUE | no | game value id does not exist | use an id from the value catalog |
| UNKNOWN_VALUE_TYPE | no | the value is `true`/`false`, a nested array, or an object without a type key | use section 4.1 |
| UNKNOWN_ARGUMENT | no | argument key not in the action (it is ignored) | use the keys from the message |
| UNKNOWN_MARKER | no | switch key not in the action (it is ignored) | use the listed marker keys |
| UNKNOWN_TARGET | no | target not in the list for this node | use section 5.3 |
| WRONG_VALUE_TYPE | no | value type does not fit the argument | use section 4.2 |
